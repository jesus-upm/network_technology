1. Theoretical part

1.1Transport layer and ports

The transport layer provides communication between processes on different hosts, while the network layer (IP) only delivers packets between hosts. The two main transport protocols of the TCP/IP stack are TCP and UDP.

A port is a 16-bit number (0–65535) that identifies an application or service on a host. A connection is identified by the socket pair: source IP + source port + destination IP + destination port (+ protocol). Port ranges (IANA):

Range Name Use
0–1023 Well-known (system) ports Standard services: 21 FTP, 22 SSH/SCP/SFTP, 53 DNS, 80 HTTP, 443 HTTPS
1024–49151 Registered ports Applications registered with IANA
49152–65535 Dynamic (ephemeral) ports Chosen by the OS for the client side of a connection

1.2TCP protocol

The Transmission Control Protocol (RFC 9293) is connection-oriented and reliable. It delivers a byte stream in order and without duplicates, using sequence numbers, acknowledgements, retransmission of lost data, flow control (receiver window) and congestion control. It is used where correctness matters more than minimal delay: web (HTTP/HTTPS), e-mail, FTP, SSH.

1.3UDP protocol

The User Datagram Protocol (RFC 768) is connectionless and unreliable (best effort). Every datagram is sent independently: no handshake, no acknowledgements, no retransmission, no ordering, no congestion control. In exchange it has very low overhead and latency. It is used for DNS queries, DHCP, VoIP, video streaming, online games and QUIC.

1.4TCP protocol parameters (header fields)

The TCP header is 20 bytes long, up to 60 bytes with options.

Field Size Meaning
Source port 16 bits Port of the sending process
Destination port 16 bits Port of the receiving process
Sequence number 32 bits Number of the first data byte in the segment (or the initial sequence number in a SYN)
Acknowledgement number 32 bits Next sequence number the sender expects to receive (valid when ACK is set)
Data offset 4 bits Header length in 32-bit words
Flags 8 bits CWR, ECE, URG, ACK, PSH, RST, SYN, FIN
Window size 16 bits Number of bytes the receiver is willing to accept (flow control)
Checksum 16 bits Error detection over header, data and pseudo-header
Urgent pointer 16 bits Offset of urgent data (valid when URG is set)
Options 0–320 bits For example MSS, window scale, SACK permitted, timestamps

1.5UDP protocol parameters (header fields)

The UDP header is only 8 bytes long.

Field Size Meaning
Source port 16 bits Port of the sender (optional, may be 0)
Destination port 16 bits Port of the receiver
Length 16 bits Length of header + data in bytes
Checksum 16 bits Error detection (optional in IPv4, mandatory in IPv6)

1.6Comparison of TCP and UDP

Feature TCP UDP
Connection Connection-oriented Connectionless
Reliability Acknowledgements, retransmissions None
Ordering Guaranteed Not guaranteed
Flow / congestion control Yes No
Data unit Byte stream (segments) Datagrams with preserved boundaries
Header size 20–60 bytes 8 bytes

1.7TCP connection

A TCP connection is a full-duplex, logical channel between two sockets. It has three phases: establishment, data transfer and release. During its life each side goes through states such as LISTEN, SYN_SENT, SYN_RECEIVED, ESTABLISHED, FIN_WAIT_1/2, CLOSE_WAIT, LAST_ACK, TIME_WAIT and CLOSED. These states are what netstat shows in the practical part.

1.8Connection establishment: three-way handshake

  • SYN: the client sends a segment with SYN set and its initial sequence number (ISNc).
  • SYN-ACK: the server answers with SYN and ACK set, its own initial sequence number (ISNs) and acknowledgement number ISNc+1.
  • ACK: the client confirms with ACK set and acknowledgement number ISNs+1. The connection is now ESTABLISHED on both sides.

Three messages are needed so that both sides agree on each other's initial sequence numbers and confirm that the other side can send and receive.

1.9Connection release

The normal release is a four-way handshake, because each direction is closed independently:

  • Side A sends FIN (it has no more data to send) and enters FIN_WAIT_1.
  • Side B sends ACK; A enters FIN_WAIT_2, B enters CLOSE_WAIT.
  • When B has finished sending, it sends its own FIN (LAST_ACK).
  • A sends the final ACK and waits in TIME_WAIT (2×MSL, typically 30–120 s) so that late segments expire and a lost final ACK can be retransmitted. Then the connection is CLOSED.

A connection can also be aborted immediately with a RST segment.

2. Practical part

2.1.1Web browsing (www.google.com)

Method. Open www.google.com. In a terminal run netstat -ano (Windows) or netstat -tunap (Linux). In Wireshark use the filter tcp.port == 443 (or quic for UDP 443 if your browser uses HTTP/3). Then close the browser and run netstat again.

Expected result. Remote port 443 (HTTPS, TCP); local port is ephemeral. After closing, entries move to TIME_WAIT and then disappear.

2.1.2FTP file transfer

Method. Connect with an FTP client (for example ftp studife.it.p.lodz.pl), upload a file with put, then quit. Wireshark filter: ftp || ftp-data or tcp.port == 21. Check netstat before, during and after.

Expected result. Control connection: remote port 21. Data connection: in passive mode the client connects to a high server port announced in the reply to PASV; in active mode the server connects from port 20 to a port given by PORT. FTP sends credentials and data in plain text, visible in Wireshark.

Expected result. One TCP connection to remote port 22 (SSH) with an ephemeral local port. Control and data travel through the same encrypted channel, so, unlike FTP, no content is readable in Wireshark.

2.1.4DNS transport protocol and port

Method. Start Wireshark with the filter dns, then run nslookup www.google.com (flush the cache first, for example ipconfig /flushdns on Windows). Inspect the UDP header of the query and the response.

Expected result. DNS uses UDP port 53 on the server (the query's source port is ephemeral, and the response comes from port 53). TCP port 53 is used when a response is too large (TC bit set), for zone transfers, and in some secure DNS setups.
